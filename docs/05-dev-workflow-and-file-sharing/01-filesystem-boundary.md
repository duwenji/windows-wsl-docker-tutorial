# 01 ファイルシステムの境界

## 所要時間

約15分

## 学習目標

- WSL2内のLinuxファイルシステムとWindows側からの見え方の違いを説明できる
- 9pプロトコル越しのアクセスが遅い理由を説明できる

---

## 2つのファイルシステム

WSL2には、性質の異なる2つのファイルシステムへのアクセス経路があります。

- **WSL2内のLinux ext4ファイルシステム**（`/home/<user>/...`）: WSL2 VM内に実体があるネイティブなLinuxファイルシステム
- **Windows側ファイルシステム**（`/mnt/c/...`）: Windowsの`C:\`ドライブなどを、WSL側からマウントして見えるようにしたもの

逆に、Windows側からWSL内のファイルを見る場合は `\\wsl$\Ubuntu\home\<user>\...` や `\\wsl.localhost\Ubuntu\home\<user>\...` というネットワークパス経由でアクセスします。

💡 2つの表記があるのは、`\\wsl$\`が先に導入された古い表記で、`\\wsl.localhost\`が後から追加された現行の表記だからです。`\\wsl$\`は一部のアプリケーションでネットワークドライブと誤認識されるなどの問題があったため、現在は`\\wsl.localhost\`の使用が推奨されています。エクスプローラーのアドレスバーに`\\wsl.localhost\Ubuntu\home\<user>\`と入力すれば、WSL内のファイルをGUIで直接参照できます（両方とも同じ場所を指しており、動作に実質的な違いはありません）。

## 9pプロトコル越しのアクセスが遅い理由

WindowsのプロセスからWSL内のLinuxファイル（またはその逆）にアクセスする場合、`9p`というネットワークファイルシステムプロトコルを介した変換が発生します。これは本来リモートファイルシステム用に設計されたプロトコルであり、通常のローカルファイルアクセスに比べてオーバーヘッドが大きくなります。

特に、`node_modules`のような大量の小さいファイルを読み書きする操作（`npm install`など）では、このオーバーヘッドが積み重なり、体感できるレベルで遅くなります。

## 実測で確認する

WSL側ファイルシステムとWindows側ファイルシステムで、同じ操作を比較してみます。

```bash
# WSL側ネイティブファイルシステムの場合
mkdir -p ~/perf-test && cd ~/perf-test
time (for i in $(seq 1 1000); do touch file_$i.txt; done)
```

```bash
# Windows側ファイルシステム（/mnt/c/経由）の場合
mkdir -p /mnt/c/Users/<ユーザー名>/perf-test && cd /mnt/c/Users/<ユーザー名>/perf-test
time (for i in $(seq 1 1000); do touch file_$i.txt; done)
```

`real`の時間を比較すると、`/mnt/c/`配下のほうが明確に遅いことが確認できます。

## 推奨: プロジェクトはWSL側のファイルシステムに置く

この性能差を踏まえ、開発プロジェクトは`/mnt/c/...`ではなく、**WSL側のファイルシステム（`/home/<user>/...`）に置く**ことを推奨します。VS CodeのRemote-WSL拡張（02章参照）を使えば、Windows側で普段通りにエディタを操作しながら、実体はWSL側に置くことができます。
